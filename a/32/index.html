引擎选型与并发压测：同一个模型换个框架，吞吐差一个数量级

2026 年 9 月 27 日约 14 分钟炼丹笔记 本地部署 推理引擎 vLLM

先摆一组实测结局，它是整篇的引信。

一份第三方实验室的对比，用同一个 32B 模型做 50 路并发压测。结论是：两个服务端引擎分别跑出 418 tok/s 和 392 tok/s 的聚合吞吐，而那个我们在上一篇里好不容易配好的 Ollama，94 tok/s，并且 50 条连接里有 6 条直接超时。

模型一行没改，卡一张没加。差的只是搬运这批货的工具。

⚠️ 这份对比用的是几年前的旧版本号（SGLang v0.3.2 / vLLM v0.8.1 / Ollama v0.9.4），量级可以参考，倍数别当真。但它揭示的那件事是真的：Ollama 从来没被设计来干这个活。

一个比喻：家庭厨房和中央厨房

给你自己做饭，一把刀一口锅就够了。你想什么时候放盐就什么时候放，锅空着也没人管。

给一百个人同时供餐，问题全变了。你得考虑备料顺序、几口灶同时开谁先用、招牌菜的汤底要不要熬一大锅共用、以及一个人点多了别人要不要等。

区别不在厨师的手艺，在组织方式。

推理引擎做的就是这份组织工作。模型（厨师）还是那个模型，但它决定三件事：显存怎么切给谁、谁排在谁前面、已经算过的东西能不能 reuse。

核心分歧只有两个字：KV 怎么管

上一整篇《推理炉具七层》反复证明了一件事：解码阶段的瓶颈是 KV 缓存，不是算力。 所以引擎之间真正的差别，几乎全在 KV 缓存的管理方式上。

两个主流流派，看名字就知道对方的思路。

vLLM 的 PagedAttention，把 KV 当内存分页

思路直接借操作系统的虚拟内存。把 KV 切成固定大小的小块，按需分配，用完回收。

它带来的三个好处是连锁的。

按需分页  →  几乎没有碎片（官方称浪费低于 4%）
         →  能同时驻留更多请求
         →  空闲块直接还给调度器

还有个巧妙的副产品：引用计数 + 写时复制。多个请求共用同一段前缀时，物理块只存一份，谁要改才分裂出自己的副本。官方给的数字是这种做法最多省 55% 的显存，并在特定 benchmark 下拿到最高 2.2 倍的吞吐提升。

代价是它按块对齐做前缀复用。你的前缀必须整齐地落在块边界上，命中才算数。

SGLang 的 RadixAttention，把 KV 挂在一棵前缀树上

SGLang 维护一棵基数树（radix tree），每个请求进来就沿着这棵树找「我这个序列和树里现有的最长公共前缀是什么」，命中就直接复用，不需要任何配置，也能认分叉的对话历史。

对比一下两者的工作方式。

vLLM PagedAttention SGLang RadixAttention
数据结构 固定大小的块 + 块表 一棵覆盖所有历史的前缀树
复用粒度 按块对齐 任意深度、逐 token
淘汰策略 按块回收 类似 LRU，会剪掉远端的叶子
分叉对话 需要自己命好 天然支持
额外配置 --enable-prefix-caching 默认就有

那一批 Agent 场景（长系统提示、每轮都重复的工具 schema、多轮循环）之所以普遍偏向 SGLang，根源就在这棵树上。

但要泼一盆冷水：RadixAttention 论文里那个「最高 6.4 倍」的数字，指的是极端前缀共享的极端负载。 真实混合流量上，第三方复现出来的量级要温和得多。这件事我们下一节用数据说话。

五个选手怎么分工

把桌子上这几个都摆出来。版本号取自各项目 GitHub Releases API，查证时间是 2026 年 10 月初，请自行复核。

引擎 当前版本 协议 该干的事 不该干的事
Ollama v0.40.0（09-25） MIT 开发机、单人/小团队、脚本与 Agent 接入 生产大并发
llama.cpp v0.6.0（10-05） MIT CPU / Mac / 边缘设备、GGUF 生态的地基 多用户调度（它不做服务）
vLLM v0.31.0（10-05） Apache 2.0 通用服务端首选，模型与硬件覆盖最广 极端前缀复用的极致优化
SGLang v0.5.21（10-02） Apache 2.0 Agent、多轮、结构化输出 追求最大生态时
LMDeploy v0.18.0（09-28） Apache 2.0 单卡 AMPERE/Ada 上的高效部署，国产卡与特定后端的路子 —

几个补充判断。

llama.cpp 是地基而不是对手。 Ollama 跑的就是它的引擎。它支持的后端是全谱系里最宽的（CUDA、Metal、Vulkan、SYCL、HIP、OpenCL、WebGPU，加上 CPU 上的 AVX/AVX2/AVX512/NEON），纯 CPU 和树莓派场景它无敌。但它定位是「跑得动」，不是「多人排队等着用」。

LMDeploy 值得单独看一眼。 它自带 TurboMind 这条高度优化的 C++ CUDA 路线，在低延迟单卡上有自己的优势，而它这一版里还在修 NPU 相关的问题，走的正是多后端路线。做国产化部署时它是一条绕不开的路，下一篇会详谈。

版本这个东西，别信二手。 网上的文章里同一个项目能同时出现三四个版本号互相打架。下单之前去 release 页面亲眼看一下，这五秒钟比什么都值。

实测数据，以及它真正的结论

先看一组流传较广的 H100 数据（8B 模型、ShareGPT 混合流量）。

引擎 聚合吞吐
SGLang（RadixAttention） 约 16,200 tok/s
vLLM（PagedAttention） 约 12,500 tok/s
TGI 约 9,800 tok/s

看起来 SGLang 领先 29%，可以下单了。别急，我们把流量形状换一下再看。

同一批第三方评测给出的另外两个结论，才是真正值钱的部分。

结论一：前缀不重叠时，两者基本持平。 一堆互不相同的独立请求压上去，差距是 2% 到 5%，落在每次测试的波动范围内。

结论二：模型变大之后差距收窄。 到 70B 这个量级，负载从「卡在显存」变成了「卡在算力」，两种缓存策略趋同，有时反而是 vLLM 的批调度略优一点。

还有一组更贴近交互的三方测试，10 路并发下的首字延迟是 TensorRT-LLM 105ms、SGLang 112ms、vLLM 120ms。在毫秒级的差距上谈胜负，不如回去再看一眼你自己的日志。

这才是这批数据唯一的结论：决定胜负的不是引擎，是你的流量形状。请先去量你的前缀命中率，再挑引擎。为别人的头条数字做迁移决策，是所有选型里最贵的一种。

怎么量那个命中率

vLLM 给了两个开关，把这件事从玄学变成了可以读的数。

vllm serve /models/Qwen3.5-35B-A3B \
  --enable-prefix-caching \
  --enable-prompt-tokens-details

开了之后，接口的 usage 里会多出一段明细。

"prompt_tokens": 12543,
"prompt_tokens_details": {
  "cached_tokens": 11204,
  "new_tokens": 1339
}

命中多少一目了然。 有一份自建环境的记录可以参考：一台四卡机器上跑 27B 模型，连续跑四天，整体前缀命中率在 43% 到 45%。而在单卡 Agent 场景的一次极端重放里（15 万 token 的固定提示），开了缓存之后耗时从 53.2 秒掉到 2.3 秒，命中率 93.5%。

如果命中率还不到两成，别急着换引擎，先去改你的提示词。 比如把系统提示里那个每次都在变的时间戳拿掉——前缀必须逐字节一致，一个字符变了整段缓存就废了。

压测怎么测才不算白测

四个必须盯的数。吞吐、首字延迟 TTFT、字间延迟 ITL、P95 延迟。 少了任何一个，你都可能被自己的平均值骗过去。

三条比这些数字更重要的纪律。

纪律一：用真实流量形状。 拿一堆随机长度的 prompt 压出来的数字，和你线上那种「3 万 token 系统提示 + 每轮追加」的形状，可能差一个数量级。先把真实请求的分布抓一遍，照着它造压测集。

纪律二：必须测满到「开始掉东西」为止。 很多人都只测到「稳定区」就收工了。请一路加上去，把曲线打到拐弯：拐点在哪、开始抢占了没有、掉下去的是延迟还是请求。

python -m vllm.entrypoints.openai.api_server  # 服务端
python benchmark_serving.py \
  --backend vllm --model your-model \
  --dataset-name sharegpt --dataset-path ./ShareGPT_V3.json \
  --num-prompts 1000 --request-rate 32 \
  --percentile-metrics ttft,tpot,itl,e2e

纪律三：长跑。 前面那份跑了一个月的测试里，三个引擎各出过不同的幺蛾子：有的在复杂多模态分支上会出现引用计数不释放，得每周重启一次；有的在和别的应用共用机器时表现不佳。这些只有长跑能发现，跑十分钟是看不见的。

一条能算出并发上限的公式

终于到了本篇最实用的部分。把第一篇那个脚本和数字接过来，可以推出一条能直接用的公式。

并发上限 ≈ (可用显存 − 权重 − 运行时开销) ÷ (每 token KV × 平均上下文长度)

括号里的每一项都有出处，没有一个数是拍脑袋的。拿一张 32 GiB 的卡举个完整例子。

可用显存      32 GiB × 0.90（gpu-memory-utilization）= 28.8 GiB
模型权重      35B-A3B 的 Q4_K_M，约 21.4 GiB
运行时开销    约 1.0 GiB
────────────────────────────────────────
留给 KV       6.4 GiB

每 token KV   48 KiB（这个值由第一篇脚本读 config.json 算出来）
平均上下文    8,192 token
────────────────────────────────────────
单路占用      8192 × 48 KiB = 384 MiB = 0.375 GiB
并发上限      6.4 ÷ 0.375 ≈ 17 路

十七路。 就这样。

这张卡看着不小，能服侍的并发其实是个位数到十位数。理解了这一点，你就再也不会问出「为什么我们加了卡，用户还是说慢」这种问题了 —— 因为答案从来不在卡的数量，在这条公式的分母上。

三条降低分母的路，按顺序。

手段 效果 代价
KV 精度降到 fp8 分母直接砍半 质量损失极小，仍要先把你的任务测一遍
前缀缓存 重复部分不占空间也不重算 要求前缀逐字节一致
把平均上下文压下来 线性下降 需要改提示词设计或改走 RAG

一份可以直接投产的配置

vLLM 的启动，注意按顺序加，每加一项测一次。

vllm serve /models/Qwen3.5-35B-A3B \
  --host 127.0.0.1 --port 8000 \
  --served-model-name internal-assistant \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --max-num-batched-tokens 8192 \
  --enable-prefix-caching \
  --enable-prompt-tokens-details \
  --kv-cache-dtype fp8_e5m2 \
  --disable-log-requests

然后是四个一个都不能少的服务件。

  • 鉴权。引擎原生接口同样不带锁。--api-key 或者挡一层网关，二选一；
  • 限流。按上面算出来的并发上限设一个略低的阈值，超限直接返回 429，别让它排队排到超时；
  • 监控。引擎自带的 Prometheus 端点要接到 Grafana 上，盯住显存占用率和抢占次数这两个和用户体感直接相关的数；
  • 优雅重启。用 systemd 托管，配 Restart=on-failure，并设置好 TimeoutStopSec 让它有机会把在跑的请求打完。

有一份提及的知识点值得放在这里：PagedAttention 在极短输入（不到 64 个 token）上反而可能吃亏，块表和查表的开销占比会高到明显。你若是大量几十 token 的分类请求，先小规模跑一组对照，别默认它一定更快。

炼丹小结

  1. 并发场景下的差距是数量级的，但差距的来源是流量形状而不是引擎本身；
  2. PagedAttention 按块复用，RadixAttention 按树逐层复用，后者天生适合 Agent 和多轮；
  3. 前缀互不重叠时两者差 2% 到 5%，在噪声里；模型到 70B 之后差距还会进一步收窄；
  4. 决策前先量前缀命中率，不到两成就先改提示词，别急着换引擎；
  5. 五个引擎各安其位：开发机 Ollama，边缘 llama.cpp，通用服务端 vLLM，Agent 场景 SGLang，国产化与单卡高效部署看 LMDeploy；
  6. 压测必须用真实流量形状，必须测到拐点，必须长跑；
  7. 并发上限 = (可用显存 − 权重 − 开销) ÷ (每 token KV × 平均上下文)，每一项都能自己算出来；
  8. 降分母的优先级是 KV 精度 → 前缀缓存 → 缩短平均上下文；
  9. 生产的四个必装件：鉴权、限流、监控、优雅重启;
  10. 版本号自己去看 release 页，二手文章里的版本号经常在打架。

同一个模型换个框架能差一个数量级，这不是玄学，是同样一块显存被组织方式决定了能装下多少同时在跑的请求。
