推理炉具七层：同样的模型，为什么别人快十倍

2026 年 9 月 27 日约 9 分钟炉具评测 推理优化 vLLM 量化 部署

有个真实的对比：同一个 70B 模型，同一个任务——

朴素部署 优化后
响应耗时 4.8 秒 280 毫秒
GPU 利用率 22% 68%

模型没换，卡没加。 差的只是「炉具」——也就是怎么把它跑起来。

这一篇讲七层优化，按实施顺序排，越靠前越便宜、收益越大。

先泼一盆冷水：先测，别急着买卡

瓶颈经常不在模型上——可能在分词、在请求排队、在网络、在预处理。没测就动手，等于蒙眼调火。

# 用真实流量跑一遍拿基线
python benchmark_serving.py --model your-model \
  --num-prompts 1000 --request-rate 10 \
  --input-len 512 --output-len 256

四个必须盯的数：吞吐（token/s）、首字延迟 TTFT、字间延迟 ITL、P95 延迟。

没有基线，后面每一层优化都是在猜。

第一层：连续批处理 = 让 GPU 别空跑（拼车）

问题：朴素部署一次处理一个请求。前一个还没写完，后面的全在排队——GPU 大部分时间在等。

解法：连续批处理（Continuous Batching）。

比喻：出租车拼车。一辆车不等客满就走，路上有人下车就补人上来，始终满载。

朴素批处理 连续批处理
GPU 利用率 常常 20～30% 60～90%
每 token 成本 基准 通常降 40～60%
质量损失 — 零（同样的计算，只是排得更满）

这是第一优先级的优化：零质量损失，收益巨大。

做法就是别用裸 model.generate()，换成 vLLM 或 SGLang。换框架本身，往往就是最大的一次提速。

  • vLLM：通用默认，硬件和模型覆盖最广；
  • SGLang：如果你的流量是「大量请求共享长前缀」（RAG、多轮对话、固定系统提示），它的缓存管理能显著更高吞吐，值得专门测一下。

第二层：量化 = 把精装书换成平装（省显存）

模型默认用 FP16（半精度）存权重。量化就是用更少的比特存同一个数。

比喻：精装书换成平装书——内容一样，更轻更薄，搬起来快，代价是纸张差一点。

精度 显存 质量 建议
FP16（默认） 基准 基准 —
FP8 约省一半 实测基本无损 H100/H200 上直接上
INT8 更省 需校准验证 A100 上考虑
INT4（AWQ/GPTQ） 最省 损失可达 2% 量级 必须按任务验证后再上生产

实用原则：同一族模型、不同场景给不同精度。 客服对话走 FP16；内部知识库问答走 INT4；做数学的别碰低精度。

第三层：前缀缓存 = 常用开头不用重算

如果你的每个请求都以同一段系统提示开头（绝大多数线上服务都是），那么这段前缀的 KV 缓存完全可以复用。

比喻：每次开会都念同一段开场白——念一次录下来，以后直接播录音。

这是 RAG 和多轮对话场景下性价比最高的一招，通常改动极小（加个启动参数）收益极大。

⚠️ 前提：前缀必须逐字节一致。系统提示里插了个时间戳，缓存就全废了（见《上下文工程》）。

第四层：KV cache 量化 = 草稿纸也用薄一点的

推理时模型要把「前面所有字」的中间结果缓存下来，这就是 KV cache。长对话时它占的显存远超模型本身。

把 KV cache 也量化成 FP8，显存省一半 → 同样的卡能跑更大的批 → 吞吐直接上去。

第五层：投机解码 = 实习生起草，老板审稿

问题：大模型是一个字一个字往外吐的，每个字都要整个模型跑一遍，慢。

解法：投机解码（Speculative Decoding）。

比喻：实习生先起草一段，老板一次性审稿通过——通过的就白赚，没通过的打回重写。

小模型（快）起草 5 个字 → 大模型（准）一次性验证这 5 个字
    ├─ 全对 → 一次前向出了 5 个字，血赚
    └─ 第 3 个字错了 → 前 2 个保留，从第 3 个重来

上线判据：在你的真实流量上测接受率，高于 0.65 才值得上，并持续监控。

两个实践细节：

  • 起草模型要同族（70B 配 8B，别跨家族），否则接受率会崩；
  • 给尾延迟加降级开关：投机解码的耗时方差更大。设一个 1.5 倍预期耗时的超时，超了就退回标准解码——这一条救过我们的 P99。

第六层：级联路由 = 小病社区医院，大病三甲

前面五层都是「让单次推理更便宜」。第六层是**「让便宜的活别找贵的模型」**：

简单/高频（分类、抽取、摘要、格式化）  →  小模型
复杂推理、长程规划、难题                →  大模型

这一层通常还能再压掉一大截成本，而且它跑在推理引擎之上，跟前面几层自由叠加。

关于自托管还是用 API：业内常提的经验阈值是月 API 支出到几万美元量级以上，且存在质量相当的开源模型、团队也有运维能力时，自托管才开始划算。在这个规模以下，先做好缓存和路由，ROI 远高于自己养卡。

别忘了算运维成本：GPU 集群、更新流水线、值班响应——至少一位资深 infra 工程师。

第七层：prefill/decode 分离（大规模才用）

「读题」和「写字」两个阶段的计算特性完全不同：

  • prefill（读题）：计算密集，能塞满 GPU；
  • decode（写字）：访存密集，GPU 核心在等显存。

把它们放到不同的 GPU 池里各自优化，能榨出最后一点性能——但100 张卡以上才划算，小规模别折腾。

真正的天花板：不是算力，是 KV cache

这一节是整篇最值钱的部分。

很多人以为推理的瓶颈是算力不够。解码阶段不是——它卡在显存带宽上。

一个常被引用的算例：80GB 显卡跑 7B 模型、4K 上下文——算力足够支撑上百个并发，而 KV cache 在十几个并发就撑不住了。差一个数量级。

决定你并发上限的是 KV cache 装得下多少，不是你的卡有多快。

这解释了为什么第四层（KV cache 量化）收益那么大：省下的显存直接换成批大小。

那个必须盯住的悬崖

推理框架会一直接请求，直到 KV cache 填满。一旦越过 100%，它开始驱逐正在跑的请求——这些请求的缓存被丢掉，恢复时要重算，延迟大约翻倍。

甜点位置是贴近但不超过 100%。两个救命指标：

指标 怎么看 异常意味着
kv_cache_usage_pct 调参数让它高但稳定 持续打满 → 已在悬崖边
num_preemptions 应该接近 0 持续上涨 → 已经掉下去了

一份可抄的启动参数

vllm serve /models/your-model \
  --tensor-parallel-size 2 \
  --max-num-batched-tokens 8192 \
  --max-num-seqs 64 \
  --enable-chunked-prefill \
  --gpu-memory-utilization 0.92 \
  --kv-cache-dtype fp8_e5m2 \
  --enable-prefix-caching \
  --speculative-model /models/your-draft-model \
  --num-speculative-tokens 5

几个门道：

  • --gpu-memory-utilization：从 0.85 起步慢慢加，给激活值留余地，否则长序列直接 OOM；
  • --max-num-batched-tokens：默认 2048 太保守，调到 8192 常常就能上 3 倍；
  • --tensor-parallel-size：用能装下的最小 TP，TP=2 常常好过 TP=4（通信不是白给的）；
  • --num-speculative-tokens：接受率低就从 5 降到 3。

炼丹小结：按顺序上，每加一层测一次

  1. 先测，拿基线；
  2. 换 vLLM/SGLang + 连续批处理（零损失，收益最大）；
  3. 量化：FP8 起步，INT4 必须验证；
  4. 前缀缓存（共享前缀场景的免费午餐）；
  5. KV cache 量化，把省下的显存换成批大小；
  6. 投机解码（接受率 > 0.65 才上，加超时降级）；
  7. 级联路由，让便宜的活找便宜的模型；
  8. 时刻盯住 kv_cache_usage_pct 和 num_preemptions。

4.8 秒和 280 毫秒之间，隔着的往往不是黑科技，就是这七层有没有按顺序开。
