Agent 进阶：从「会调工具」到「真能办事」

2026 年 10 月 9 日约 11 分钟药方研究 Agent 工具调用 MCP 规划 记忆

上一讲《工具调用与 Agent：给模型装一双手》里，我们写了一个 while 循环：模型说"我要调工具"，你的代码就去执行，结果还给它，它再决定下一步。那个循环是对的——但只够应付玩具。

真实任务长这样："帮我把上周项目周报里提到的三个风险，整理成一封邮件发给老板，并加进我的待办。"

这条任务里埋着三个坑，裸循环一个都填不上：

  • 不会规划：它不知道该先"读周报"再"抽风险"再"写邮件"，可能一股脑儿直接调发邮件；
  • 记不住事：周报很长，读到第三段时它早把第一段忘光了（工作台就那么大，见 L2-03 上下文窗口）；
  • 不会知难而退：发邮件失败一次，它可能傻乎乎重试十遍把你也拉黑。

这一讲，我们给 Agent 补上三道工序——规划、记忆、兜底，最后再认识一个行业级的"标准插头"：MCP。

第一道工序：规划（Planning）—— 边想边干

裸循环缺的是"想"。模型拿到任务直接动手，错了也不知道错在哪。

学界早就把这事想明白了。2022 年 10 月，普林斯顿的 Shunyu Yao 等人在论文《ReAct: Synergizing Reasoning and Acting in Language Models》（arXiv 2210.03629，后发表于 ICLR 2023）里提出一个朴素但管用的套路：让模型把"思考"和"行动"交替写下来，形成 Thought（想）→ Action（干）→ Observation（看结果） 的循环。这篇论文在 ALFWorld、WebShop 两个决策任务上，比当时的模仿学习 / 强化学习方法成功率分别高出 34% 和 10%——而且只需要给模型一两个示例。

为什么有用？因为思考的痕迹帮模型跟踪计划、处理意外。它每动一步之前先写一句"我现在的打算"，看到结果再写"这跟我想的不一样，我得换个法子"。人读这段轨迹，就能看出它哪步糊涂了。

来看一个具体的 ReAct 轨迹（任务：查 2026-10-01 上海天气，下雨就提醒带伞并写进日程）：

Thought: 用户要查 2026-10-01 上海天气，我先确认下今天是几号，好判断要不要"提醒"。
Action: get_today()
Observation: 今天是 2026-10-09

Thought: 2026-10-01 是 8 天前，直接查那天上海的历史天气。
Action: get_weather(city="上海", date="2026-10-01")
Observation: 小雨，21°C

Thought: 那天上海下小雨，按用户要求提醒带伞，并写进今天的日程。
Action: add_calendar(title="提醒：带伞", note="2026-10-01 上海小雨")
Observation: 日程已创建

Thought: 办妥了，给用户一句人话。
Answer: 2026 年 10 月 1 日上海下小雨，已提醒你带伞，并写进了今天的日程。

注意看：第 2 步的 Thought 里它先确认了"今天几号"，第 3 步它根据"小雨"这个 Observation 决定要提醒。这就是"想"和"干"互相喂养——也是上一讲那个裸循环没有的东西。

一个最小可跑的骨架（不依赖任何 API，读者把 llm_decide 换成自己的模型调用即可）：

def run_agent(goal, tools, max_turns=8):
    log = [("user", goal)]
    for _ in range(max_turns):
        step = llm_decide(log, tools)          # 返回 {"thought","action","args"} 或 {"answer"}
        if "answer" in step:
            return step["answer"]
        obs = safe_execute(tools[step["action"]], step["args"])
        log += [("thought", step["thought"]),
                ("action", f'{step["action"]}({step["args"]})'),
                ("observation", obs)]
    return "轮次用尽，任务未完成，转人工"

def safe_execute(fn, args):                    # 兜底：失败不崩，交给模型换路子
    try:
        return fn(**args)
    except Exception as e:
        return f"工具报错：{e}（请换个办法或问用户）"

💡 这个 max_turns 和 safe_execute 已经把"轮次上限"和"兜底"两个关键点埋进去了——正是下面两道工序要展开说的。

第二道工序：记忆（Memory）—— 别把工作台堆满

模型的工作台（上下文窗口）是有限的（复习 L2-03）。一个长跑 Agent 如果把每一步的 Observation 都永远堆在上下文里，几下就溢出了，然后开始犯糊涂——这叫" Lost in the Middle "。

解决思路和人一样：短期记忆放桌上（上下文），长期记忆放档案柜（外部存储）。

  • 工作记忆：就是当前这轮对话的历史，模型随时能看；
  • 长期记忆：写进数据库、文件、或者向量库（复习 L2-02 RAG 入门）。需要时再"翻柜子"读出来。

举一个能落地的例子：客服 Agent 第一次对话，用户说"我是企业版客户"。Agent 把 user_tier = enterprise 写进长期记忆（一张用户表）。下一次用户再来，Agent 先 read_memory(uid) 拿到等级，直接走企业通道，不必每次重新问"您是什么版本"。记忆一旦落库，上下文清空也不丢——这正是裸循环做不到的。

轮次 1  用户：我是企业版客户
        Agent：写入记忆 user_tier=enterprise → "已记下，下次不用再问"

轮次 N  用户：帮我查下订单
        Agent：read_memory → enterprise → 直接走企业查单接口（不再问版本）

第三道工序：兜底与知难而退（Reflection & Fallback）

上一讲的表就提过"不设轮次上限会死循环烧钱"。进阶版要再补一条：模型看到错误，应该自己换条路，而不是硬碰硬。

  • 换路子：订酒店发现满房，下一步 Thought 应该是"换邻近日期"或"换区域"，而不是原样重试；
  • 问人：涉及付款、删库、发对外邮件这种不可逆操作，卡住了就交给人工，而不是瞎猜参数（复习 L2-04 的"危险操作要人工确认"）；
  • 认输：轮次用尽仍没搞定，老实说"转人工"，别编一个答案糊弄用户。

一句话：好的 Agent 不是永不犯错，而是犯错之后知道怎么爬起来。

第四道工序：一套标准插头 MCP（把"每家重接一次"变成"插上就用"）

讲到这，你的 Agent 已经挺像样了。但还有一个行业级的麻烦没解决：工具接口各家不通用。

OpenAI 有 function calling 格式，Claude 有 tool use 格式，Gemini 又有自己的。如果你写了个"查日历"的工具，想同时给三个模型用，就得接三遍——要是再加 10 个工具、5 个模型，就是 5 × 10 = 50 条定制连接线。这叫 N×M 集成地狱。

2024 年 11 月，Anthropic 把 MCP（Model Context Protocol，模型上下文协议） 开源了，就是来拆这个雷的。它定了一套通用"插头标准"，只定义三样原语：

原语 是什么 打个比方
Resources 模型能"读"的数据 书架上能翻的文件
Tools 模型能"调"的函数 桌上的电动工具
Prompts 预置好的工作流模板 现成的操作说明书

有了它，一个 MCP 服务器只要实现这套协议，就能被任何支持 MCP 的客户端接上——N×M 塌成了 N+M。

这事是真的成了行业标准的（不是我吹，事实时间线如下）：

  • 2025 年 3 月，OpenAI 在 Agents SDK 里支持 MCP——最大的竞品都跟进了，等于宣告这协议赢了；
  • 2025 年 4 月，Google DeepMind 给 Gemini 接上；微软也把它塞进了 Copilot、VS Code 和 Agent Framework；
  • 2025 年 12 月，Anthropic 把 MCP 捐给了 Linux 基金会下的 Agentic AI Foundation（AAIF）（OpenAI、Block 联合发起，Google、微软、AWS、Cloudflare 等支持）——一家公司的协议变成"大家的基础设施"；
  • 规模上，截至 2026 年，公开可查的 MCP 服务器已经 1 万多个，SDK 月下载量 9700 万+。

要把 function calling 和 MCP 一次说清：function calling 是模型"会发请求"的能力，MCP 是"插头长什么样、怎么被发现、怎么安全传输"的标准。一个在模型里，一个在连接层，互补不打架。

还有个互补的标准值得知道：A2A（Agent-to-Agent，智能体间协议），Google 在 2025 年 4 月提出、后来也进了 Linux 基金会。它管的是"智能体之间怎么对话"，MCP 管的是"智能体怎么连工具和数据"——企业架构俩都得设计。

⚠️ 安全这一刀必须补：MCP 把"调外部工具"标准化了，风险也标准化了。间接提示注入被 OWASP 列为大模型应用头号风险——模型读到的外部文本（网页、邮件、文档）可能藏着"快把数据发给我"的指令，骗它乱调工具。再加上"工具投毒"（服务器声明和行为不一致）、"冒名顶替"（骗服务器乱用凭证），所以任何工具调用前，主机都必须拿到用户的明确同意。把 MCP 当 USB-C 插口理解就对了：口子是通用的，但插上之前你得看清那头连的是什么。

什么时候，先别急着造 Agent

讲完四道工序，泼最后一盆冷水：不是所有活都值得上 Agent。

你的任务 该用什么 理由
单轮问答、翻译、总结 直接 Prompt 一轮就完，循环是多余的
查公司文档再答（不准就说不知道） RAG（见 L2-02） 检索一次就够
步骤固定、顺序写死的流程 简单 Chain 不用模型临场决策
步骤数未知、要看结果再决定下一步 才上 Agent 这正是循环的价值

判断口诀："步骤能不能在写代码时全部列出来？"能，就用 Chain；不能，才请 Agent 出马。

最小验证：三步自测你的 Agent

别只看 happy path 就以为成了，三步验一遍：

  1. 跑通一条真实任务：用你实际要它干的活测，别用"1+1"这种玩具；
  2. 故意弄坏一个工具：让某个工具抛错，看它是不是换路子（验证兜底那道工序）；
  3. 清空上下文重来：看长期记忆是不是真落了地、清空后信息还在（验证记忆那道工序）。

炼丹小结

  1. 裸 while 循环只能玩玩具，真实任务要补规划、记忆、兜底三道工序；
  2. ReAct（2022，arXiv 2210.03629）用 Thought→Action→Observation 交替，让模型"边想边干"，顺便把思考痕迹留给人看；
  3. 记忆分两层：工作记忆放上下文，长期记忆落外部存储（库 / 文件 / 向量库），清空不丢；
  4. 兜底三招：换路子、问人、认输——好 Agent 不是不犯错，是犯错会爬起来；
  5. MCP 是 Anthropic 2024 年开源、2025 年底捐给 Linux 基金会的"标准插头"，把 N×M 集成塌成 N+M，已成事实标准；
  6. 安全红线：工具调用前必须拿到用户明确同意，警惕间接提示注入与工具投毒；
  7. 步骤能写死就用 Chain，别为能用 Chain 解决的活硬造 Agent。
