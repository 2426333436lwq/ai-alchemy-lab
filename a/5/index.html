炸炉实录：Agent 上线三个月，我们炸过的六次炉

2026 年 9 月 27 日约 7 分钟炸炉实录 Agent 踩坑 上下文工程

Agent 上线三个月，我们炸了六次炉。

每一次都以为「是模型不行」，每一次最后都发现是我们自己的工程问题。按代价从高到低排，全都是真金白银换来的。

一号炉：工具返回塞满窗口，模型开始「失忆」

症状：前几轮很聪明，跑到第 15 轮开始反复问已经知道的事，最后把一个早就被否掉的方案又提了一遍。

我们的误判：「这模型长上下文不行，换个窗口更大的。」

真实原因：我们的检索工具每次返回一大段原始文档，几十轮下来窗口里堆了几万 token 的工具输出，噪声把指令淹没了。模型不是失忆，是被埋了。

解法：

  1. 工具返回做裁剪，只回结构化字段，不回原文；
  2. 原始内容落盘，工具只回「路径 + 关键片段」；
  3. 给工具结果设独立预算，超限就截断并标注「（已截断，完整内容见 xxx）」。

教训：模型看得见的东西，就是你给它的全部世界。往这个世界里倒垃圾，它就会变成垃圾处理厂。

二号炉：工具描述写了一句话，模型开始编参数

症状：模型频繁用错误的参数调工具，尤其爱自己编造 ID。

我们的误判：「函数调用能力不行，多给几个示例吧。」

真实原因：我们的工具描述长这样——

{ "name": "search_database", "description": "Searches the database." }

一句话。模型除了「这是个查库的」，什么都不知道：什么时候该调、不能干什么、失败了怎么办。于是它猜，猜错了就是幻觉。

解法：把工具描述写成契约：

{ "name": "search_database",
  "description": "根据精确的 email 或 user_id 查询客户记录。\n在建议任何账户变更之前必须先调用，严禁猜测 user_id。\n最多返回 10 条，需要更多请缩小范围。\nemail 格式非法会失败，请先校验。" }

改完之后，同类错误掉了大半。

教训：工具描述就是提示词（第一层的配方原则在这里一样适用）。花十分钟重写描述，省十小时 debug。

三号炉：把 RAG 的 top-5 塞进系统提示

症状：每一轮都很贵，P95 延迟居高不下，而大多数轮次根本没用到检索内容。

我们的误判：「检索成本高是正常的。」

真实原因：我们用的是提示级 RAG——会话开始就把 top-5 文档塞进系统提示，于是每一轮都要为这 8000 个 token 付费，哪怕这一轮只是在说「好的，继续」。

解法：改成工具级按需检索——给 Agent 一个 search_docs 工具，让它自己决定什么时候查。

方式 第 1 轮 第 10 轮 相关性
提示级 RAG 8,000 8,000 靠猜
工具级 RAG 500 500（用到时 +1,200） 精准

教训：预估需求是昂贵的，按需取用是便宜的。操作系统里叫虚拟内存，Agent 里叫 just-in-time context。

四号炉：压缩时一视同仁，把决策压没了

症状：压缩之后 Agent 开始重复做已经做完的事，或者复活一个早就被否掉的方案。

我们的误判：「压缩会丢信息，那就少压一点。」

真实原因：我们的压缩是无差别摘要——把旧轮次整段丢给模型「总结一下」。而模型总结时会优先保留叙事连贯的内容（就是那些冗长的工具输出流水账），反而把决策、约束、未解决的错误压掉了。

解法：压缩必须带焦点——

summary = summarize(older, focus=[
    "decisions made",            # 做了什么决定
    "files modified",            # 改了哪些文件
    "open questions",            # 还没解决什么
    "tools that failed and why"  # 失败过什么、为什么
])

保留决策与错误（高信号），丢弃工具流水账（低信号），最近几轮保留原文。

教训：压缩不是「少写点」，是「决定什么值得一个 token」。这才是上下文工程的核心手艺。

五号炉：还没埋点就拆了多智能体

症状：拆完子 agent，效果没变好，成本翻倍，还多了两类新 bug：子 agent 结论冲突、汇总时丢信息。

我们的误判：「任务太复杂，一个 Agent 扛不住，拆。」

真实原因：我们根本没测过上下文里到底装了什么。真正的瓶颈是没压缩、没按需检索——这些便宜得多的问题没解决，直接上了最贵的一招。

解法：退回来按顺序做——

1. 先埋点：每轮进了什么？每块多大？缓存命中率多少？
          ↓
2. 再压缩 + 按需选择   ← 便宜且见效快
          ↓
3. 最后才隔离（拆多智能体）

教训：隔离有收益，但它最贵，而且会掩盖真正的问题。没仪表盘就改架构，等于没测体温就开刀。

另外也有相反的经验：如果子任务之间必须共享历史，强行拆分反而会因为「隐式决策不一致」而变差。要不要拆，取决于上下文能不能真的独立，而不是任务看上去复不复杂。

六号炉：微调之后，输出同质化得厉害

症状：在需要创意的场景（文案、头脑风暴），微调后的模型输出一模一样——同一个结构、同一批词，采样 16 条几乎分不出差别。

我们的误判：「temperature 调高一点就好了。」（没用，采样分布本身已经坍缩了）

真实原因：熵坍塌。RL 训练过程中策略分布的熵持续下降，概率全压到少数几条「最安全」的路径上。单纯把温度拉高会引入胡说，所以粗暴调 temperature 只会让它胡说八道。

解法：

  1. 训练侧：关注「只在熵骤降处精细干预」的思路，以及强制在犹豫处探索的方法；
  2. 数据侧：检查是不是简单题太多——全是简单题，模型没有探索动机；
  3. 工程侧：创意场景和严谨场景分开部署。别指望一个「推理很强」的模型同时很会写文案，这不是同一个火候。

教训：训练会让它更确定，但「更确定」不等于「更强」。pass@1 涨了而 pass@256 跌了，那是变窄了，不是变强了。

附：开炉前的自检清单

把这六次炸炉反过来，就是 checklist：

  • 工具返回有没有裁剪？原始内容是否落盘而非入窗？
  • 工具描述写成了契约，还是一句标签？
  • 检索是按需的，还是预加载后每轮交税？
  • 压缩有没有 focus？决策和错误保住了吗？
  • 上下文有没有埋点？还是直接上了多智能体？
  • 微调后有没有同时看 pass@1 和 pass@256？创意场景有没有单独验证？

写在最后

这六次炸炉，没有一次是模型的问题，全是工程问题。而且它们有个共同点——都是「偷懒」的代价：

  • 不裁剪工具输出，是因为写摘要麻烦；
  • 不写清工具描述，是因为赶时间；
  • 不埋点，是因为想直接看效果。

爬出坑的过程，往往比丹本身值钱。所以我把它们记下来。
