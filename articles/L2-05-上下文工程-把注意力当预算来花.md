上一篇我们讲了上下文窗口是**办公桌**——面积有限，摊不开的就看不见。

这一篇是进阶版：**既然桌子这么贵，怎么把它当预算来精打细算？**

## 一次代价昂贵的偷懒

先看一个真实场景。你做了一个客服 Agent，把产品手册全部塞进了系统提示：

```text
系统提示 = 角色设定 + 完整产品手册（2 万字）+ 历史对话
```

跑了几天你发现两个问题：

1. **每轮对话都很贵**——那 2 万字手册，**每一轮都要重新付费**；
2. **聊到十几轮，它开始答非所问**——手册把桌子占满了，真正的对话挤在角落里。

第 1 个问题是钱的问题，第 2 个是准确率的问题。**而这两个问题的根源是同一个：你把桌子当成了仓库。**

## 核心观念：上下文是预算，不是袋子

有个说法很贴切：

> **2024 年我们写 Prompt，2026 年我们写「产出下一个上下文的程序」。**

模型是解释器，**上下文才是程序**。每一格位置，你都得问一句：**它值这个 token 吗？**

这门手艺现在叫**上下文工程（Context Engineering）**。它接过了"Prompt 工程"的班，因为大家终于意识到：**Agent 变笨，八成不是模型不行，是喂给它的那扇窗口烂了。**

## 四招：写、选、压、隔

面对一个稀缺资源，你能做的动作其实就四个：

| 招式 | 干什么 | 大白话 |
| --- | --- | --- |
| **写 Write** | 把状态写到窗口**外面**的文件里 | 桌上放不下的，先放进抽屉 |
| **选 Select** | 只取当前这一步真正需要的 | 用什么拿什么，别一次全摊开 |
| **压 Compress** | 把旧对话蒸馏成一段摘要 | 把 50 页会议记录换成 1 页纪要 |
| **隔 Isolate** | 给子任务开一扇**独立的小窗** | 分头干活，各看各的桌子 |

### 招式一 · 写：把状态挪出窗口

最高性价比的一招。Agent 不该"扛着"全部历史跑，它该把东西**放下来**。

```text
❌ 把项目进度、已做的决策、待办事项全部留在对话里
✅ 每完成一步就写进 NOTES.md，下一步需要时再读回来
```

好处是：**压缩发生时，状态不会跟着丢**——因为它从来就不住在窗口里。

### 招式二 · 选：按需取，别预加载

回到开头那个例子。产品手册 2 万字，但**用户这一轮只是问"怎么退货"**。

```text
❌ 提示级：每轮都把整个手册塞进去      → 每轮 20,000 token
✅ 工具级：给它一个 search_manual 工具  → 每轮 500 token，用到时才 +1,200
```

**大多数轮次根本不需要检索**。为什么要让每一轮都为它付税？

> 这就是 RAG 那篇讲的思路，只是从"查文档"推广到了"查任何东西"：文件、历史记录、工具结果，都按需取用。

### 招式三 · 压：压缩要有判断力

聊到 50 轮，桌子放不下了，你得压缩。但**压缩最怕一视同仁**。

```python
def compact_history(messages, token_threshold=50_000):
    if count_tokens(messages) < token_threshold:
        return messages
    recent = messages[-6:]          # 最近 3 轮保留原文
    older = messages[:-6]
    summary = summarize(older, focus=[
        "decisions made",            # 做了什么决定 ← 高信号
        "files modified",            # 改了哪些文件
        "open questions",            # 还没解决什么
        "tools that failed and why"  # 失败过什么、为什么 ← 高信号
    ])
    return [{"role": "system", "content": f"PRIOR WORK SUMMARY:\n{summary}"}, *recent]
```

注意 `focus` 里那四项。**决策和错误是信号，冗长的工具输出是噪声。**

一视同仁地压缩，等于把丹药和药渣一起倒了——这就是为什么很多 Agent 压缩完会"重复做已经做完的事"。

### 招式四 · 隔：子 agent 开小窗

一个只知道单个文件的子 agent，比一个扛着整个代码库的主 agent 推理得更好——部分原因就是**它的窗口没烂**。

但**这是最贵的一招**（要编排、要汇总、要处理冲突），先别急着用。

## 一份预算分配表

既然是预算，就该有配额。这是长程 Agent 常用的一套分配：

| 槽位 | 放什么 | 预算 | 位置 |
| --- | --- | --- | --- |
| 系统与人设 | 角色、规则、输出契约 | ~5% | 最前（稳定） |
| 决策相关上下文 | 这一步真正需要的少数事实 | ~25% | **紧跟系统提示之后** |
| 工作集 | 当前正在操作的文件 | ~30% | 中间 |
| 近期历史 | 最近几轮（只要与决策相关的） | ~20% | 靠后 |
| **留白** | 留给模型自己思考和输出 | ~20% | **预留，绝不填满** |

由这张表推出**两条排序规则**：

**规则一：最关键的信息紧跟系统提示，别埋在中间。**
因为模型对开头和结尾利用得最好，中间最容易被忽略（上一篇讲过的 U 型曲线）。

**规则二：稳定前缀要逐字节保持一致。**
系统提示这类内容**一个字符都别改**——改一个字，缓存就整个失效，价格差一个数量级。

> ⚠️ 所以**别在系统提示里插时间戳**。很多人随手加一句"今天是 2026-09-27"，结果每轮缓存全部失效，白花一大笔钱。要传日期，放在**用户消息**里。

## 四种失效模式

窗口腐烂的方式不止一种，这四类值得记住：

| 失效 | 表现 | 典型成因 |
| --- | --- | --- |
| **中毒** | 一个错误进了上下文，后面被反复当事实引用 | 工具返回的错误结果没清洗 |
| **分心** | 历史太长，模型开始重复过去而不推进任务 | 历史占比过高，留白不足 |
| **混淆** | 工具太多太杂，模型用错了 | 工具集过大、描述含糊 |
| **冲突** | 上下文里有互相矛盾的信息，模型左右为难 | 事实更新了但旧版本没删 |

## 最常见的错误：没埋点就拆多智能体

看到这里，很多人会想："那我把 Agent 拆成多个子 agent 不就行了？"

**这是最常见的错误动作。** 隔离确实有收益，但它最贵，而且会**掩盖真正的问题**——真正的瓶颈通常是没压缩、没按需检索，那些便宜得多。

正确顺序：

```text
1. 先埋点   每轮进了什么？每个块多大？缓存命中率多少？
            ↓
2. 再压缩 + 按需选择   ← 便宜且见效快
            ↓
3. 最后才隔离（多智能体）
```

> 一句话：**先给上下文装上仪表盘，再动架构。** 没测体温就开刀，是要出事的。

## 炼丹小结

1. 上下文是**预算**不是袋子；填满 = 变笨 + 变贵；
2. 四招：**写**（外置状态）、**选**（按需取用）、**压**（保留决策与错误）、**隔**（子 agent 开窗）；
3. 排序有讲究：关键信息紧跟系统提示；**稳定前缀逐字节不变**以命中缓存；
4. **留 20% 留白**给模型思考，这 20% 绝不能填；
5. 动手顺序：**埋点 → 压缩/选择 → 隔离**。

上下文工程，说到底就是 Prompt 工程长大后该有的样子：

> **不问"这句话怎么措辞"，而问"模型下一个字会看到什么"。**

到这里，第二层就结束了。你已经能搭出一个像样的 Agent。

下一层（第三层）我们要开始**动手训练模型**——从"用模型"跨到"造模型"。
