我们先从一个真实得刺眼的场景开场。

办公室里两张一模一样的 24GB 显卡。老张在上面跑 Qwen3.5-27B 的 Q4 量化，开着 32K 上下文，还能顺手开个 IDE 不卡。你拉了个 7B 的小模型，刚把一份 40 页的 PDF 塞进去做总结，终端跳出一行 `CUDA out of memory`。

小模型被大模型挤下去了。

这不是玄学，是**你问错了问题**。「这个模型要多大显存」这句话本身就缺了三个条件：多长的上下文、几路并发、什么精度。缺了这三个，任何答出来的数字都是猜的。

## 一个比喻：这套房子里住着三样东西

把显存想成一套正在开工的房子，里面住着三家租客。

**权重是家具。** 沙发、床、冰箱，搬进来那天占多大以后就多大，一年到头不动弹。这片面积是**死的**。

**KV 缓存是工人摊在桌上的图纸。** 每接一个活就摊开一份图纸，活越多桌子占得越开，活干完了图纸收走。这片面积是**活的**，而且会随着「同时接几个活」成倍地涨。

**运行时开销是玄关和过道。** 门口那块地你放不了家具也摆不了桌子，但你要是把它占满了，人根本进不来门。CUDA 上下文、算子库的工作区、显存碎片都在这里，面积不大，漏了它你连门都开不了。

显存报 OOM 的时候，它只会给一行 `CUDA out of memory`，不会告诉你是家具买多了、图纸摊多了、还是过道被堵了。**所以这笔账只能自己算。**

## 第一笔账：权重有多重

这是唯一一眼能看到的部分。公式朴素到近乎无聊。

```text
权重体积 = 参数量 × 每个权重占几个 bit ÷ 8
```

### 先踩一遍单位坑

这里有个坑，掉进去的人比你想象的多。

| 单位 | 换算 | 谁在用 |
| --- | --- | --- |
| GB | 1 GB = 10 的 9 次方字节，正好 1,000,000,000 | 模型文件名、Hugging Face 上的文件大小 |
| GiB | 1 GiB = 2 的 30 次方字节，约 1,073,741,824 | 显卡厂商、nvidia-smi、Ollama |

显卡标的 24GB，其实是 24 GiB。同一个文件，用 GiB 表示出来的数字**永远比 GB 小 7.4% 左右**。这就是为什么模型页写着 4.9 GB，工具却告诉你它占 4.58 GiB，两边都没算错。

### 每权重占几个 bit

量化方法的名字里那个 `.89`、`.56` 不是凑整好看的，是实测出来的**每个权重的平均比特数**（bits per weight，简称 bpw）。下面是 llama.cpp 官方仓库记录的实测值，基准模型是 Llama-3.1-8B，未量化时 F16 体积 14.96 GiB。

| 量化 | bpw | 8B 模型的权重 | 相对 F16 |
| --- | --- | --- | --- |
| F16（不量化） | 16.00 | 14.96 GiB | 100% |
| Q8_0 | 8.50 | 7.95 GiB | 53% |
| Q6_K | 6.56 | 6.14 GiB | 41% |
| Q5_K_M | 5.70 | 5.33 GiB | 36% |
| **Q4_K_M** | **4.89** | **4.58 GiB** | **31%** |
| Q3_K_M | 4.00 | 3.74 GiB | 25% |
| Q2_K | 3.16 | 2.95 GiB | 20% |

验算一遍，证明这张表能自己推出来。

```text
8.03 B × 4.89 bit ÷ 8 = 4,907,000,000 字节
4,907,000,000 ÷ 1,073,741,824 = 4.57 GiB   ← 和官方表里的 4.58 GiB 对上了
```

学会了这个乘法，你看任何一个模型名都能在心里估出大小，**再也不用去翻别人整理的对照表**。

### MoE 是个显眼的例外

看到 `Qwen3.5-35B-A3B` 这种带横杠的命名，要立刻切换算法。

- **35B 是总参数**，它决定了**要交多少显存房租**；
- **A3B 是每个 token 实际用到 3B**，它决定了**吐字有多快**。

人家在你显卡上是按 35B 的重量压着（Q4_K_M 约 21.4 GiB），干活的时候每个字只用 3B 的力气。所以 MoE 模型在同等显卡上的**速度常常反超参数更小的稠密模型**，但**显存一点没省**。

反过来说，买卡的时候千万别看激活参数，那东西和显存没关系。

## 第二笔账：KV 缓存是被漏掉最多的那一笔

回到开头那个悬案。为什么 7B 会输给 27B？答案在这里。

### 公式

```text
每 token 的 KV = 2 × 层数 × KV 头数 × 每头维度 × 每个元素的字节数
```

解释一下每一项。

- **乘 2** 是因为每个字要存两份东西，一份是钥匙（K），一份是值（V），缺一不可；
- **层数**是模型有多少层，每层都得单独存一份；
- **KV 头数**这里埋了一个重要细节。现代模型普遍用 GQA（分组查询注意力），`num_key_value_heads` 远小于 `num_attention_heads`。少参数是省了权重，但 KV 这块是按 KV 头算的，**你的 head_dim 取错了整个结果就翻好几倍**；
- **每元素字节数**在 fp16 下是 2。

### 两个模型的真实对比

我们拿两个同量级的开源模型算一遍，结果挺意外。

| 模型 | 层 | KV 头 | 每头维度 | 每 token KV | 32K 上下文 × 4 并发 |
| --- | --- | --- | --- | --- | --- |
| Llama-3-8B | 32 | 8 | 128 | **128 KiB** | 16.0 GiB |
| Qwen2.5-7B | 28 | 4 | 128 | **56 KiB** | 7.0 GiB |

**参数量只差 1.3 倍，KV 缓存占了 2.3 倍。** 前者把当年全部的 32 个注意力头都用来存 KV，后者用 GQA 砍到了 4 个。

这就解释了开场那个悬案的关键一半：一个「看着差不多大」的模型，在长上下文时可以是另一个的两倍开销。

### 三种省法

**1. KV 也量化。** fp16 换成 q8_0 就砍一半，换 q4_0 砍四分之三。质量损失通常远小于把权重往下砍一档。

**2. 别迷信厂商标称的上下文。** 128K 是它的耐力上限，**不是你每天要跑的距离**。开 32K 和开 128K，KV 那块差 4 倍。

**3. 盯住并发数。** 上面那行 7.0 GiB 是「32K × 4 路」的结果。单聊的时候只用 1.75 GiB。很多 OOM 是同事也接进来用了同一张卡。

## 第三笔账：那些说不清也躲不掉的零头

家具和图纸都有公式，**这一笔只能靠经验**。

- **CUDA 上下文**，几百 MB，模型一加载就吃掉；
- **算子库工作区**，cuBLAS、cuDNN 会按设备申请缓冲，几个 GB 量级很正常；
- **prefill 阶段的激活值**，这块随「批次 × 序列长度」涨，长文档一口气塞进去时它最容易爆；
- **显存碎片**，反复加载卸载模型之后，看着有 5GB 空闲，实际申请不出一个连续的大块；
- **Windows / macOS 上还有图形界面占的那一份**，这就是为什么同一张卡在 Linux 上往往能多塞一层。

工程上给个自测得出的经验值：**打底留 1.5 到 2 GiB，再加权重的 10% 左右做缓冲。**

这个留白也是 vLLM 里 `--gpu-memory-utilization` 默认 0.9 而不是 1.0 的理由，一上来拉到 0.98 的同学基本都在长序列上翻过车。

## 一个能自己跑的脚本

存成 `vram_estimate.py`，把模型目录扔给它，全部三笔账一次算清。它优先读 `model.safetensors.index.json` 里的真实字节数，读不到才退回 config.json 推算。

```python
import json, sys, os

GiB = 1024 ** 3
USAGE = "用法：python vram_estimate.py <模型目录> <bpw> <上下文长度> [并发数] [可用显存GiB]\n" \
        "例子：python vram_estimate.py ./Qwen2.5-7B-Instruct 4.89 8192 1 24"

def load_config(path):
    c = json.load(open(os.path.join(path, "config.json"), encoding="utf-8"))
    # 多模态模型常把语言塔藏在 text_config / language_config 里
    for k in ("text_config", "language_config", "model"):
        if isinstance(c.get(k), dict) and "num_hidden_layers" in c[k]:
            base = dict(c); base.update(c[k]); c = base; break
    return c

def count_params(c):
    h, L = c["hidden_size"], c["num_hidden_layers"]
    nh = c["num_attention_heads"]
    nkv = c.get("num_key_value_heads", nh)
    inter = c.get("intermediate_size", 4 * h)
    vocab = c.get("vocab_size", 32000)
    hd = c.get("head_dim", h // nh)
    kv_dim = nkv * hd
    per_layer = (h * (nh * hd) + h * kv_dim * 2 + (nh * hd) * h
                 + h * inter * 2 + inter * h)
    total = per_layer * L + vocab * h
    if not c.get("tie_word_embeddings", False):
        total += vocab * h          # 输出层没和嵌入层共用，再算一份
    return total

def main():
    if len(sys.argv) < 4:
        print(USAGE); sys.exit(1)
    path, bpw, seq = sys.argv[1], float(sys.argv[2]), int(sys.argv[3])
    nseq = int(sys.argv[4]) if len(sys.argv) > 4 else 1
    vram = float(sys.argv[5]) if len(sys.argv) > 5 else 0.0

    c = load_config(path)
    n = count_params(c)
    h, L = c["hidden_size"], c["num_hidden_layers"]
    nh = c["num_attention_heads"]
    nkv = c.get("num_key_value_heads", nh)
    hd = c.get("head_dim", h // nh)

    w_bytes = n * bpw / 8                       # 权重
    kv_pt = 2 * L * nkv * hd * 2                # KV，默认 fp16
    kv_bytes = kv_pt * seq * nseq
    OVERHEAD = 1.5 * GiB                        # 经验值，自己调

    print(f"参数量        {n/1e9:.2f} B")
    print(f"结构          {L} 层 / {nh} 头 / {nkv} 个 KV 头 / 每头 {hd} 维")
    print(f"权重          {w_bytes/GiB:6.2f} GiB  （{bpw} bpw）")
    print(f"KV 缓存       {kv_pt/1024:.1f} KiB/token × {seq} × {nseq} = {kv_bytes/GiB:6.2f} GiB")
    print(f"运行时开销    {OVERHEAD/GiB:6.2f} GiB")
    total = w_bytes + kv_bytes + OVERHEAD
    print(f"合计          {total/GiB:6.2f} GiB")

    if vram:
        left = vram * GiB - total
        if left >= 0:
            print(f"余量          {left/GiB:6.2f} GiB  ✅ 装得下")
        else:
            print(f"缺口          {-left/GiB:6.2f} GiB  ❌ 装不下")
            print(f"  降 bpw 到 Q3_K_M 省 {n*(bpw-4.0)/8/GiB:.2f} GiB")
            print(f"  KV 转 q8_0  省 {kv_bytes/2/GiB:.2f} GiB")
            print(f"  上下文砍半  省 {kv_pt*(seq-seq//2)*nseq/GiB:.2f} GiB")

if __name__ == "__main__":
    main()
```

我们在一台真机上跑 Qwen2.5-7B，参数量算出来是 7.62 B，和官方公布的数字一致。换到「32K 上下文 × 8 路并发」这个配置，输出是这样的。

```text
参数量        7.62 B
结构          28 层 / 28 头 / 4 个 KV 头 / 每头 128 维
权重          4.34 GiB  （4.89 bpw）
KV 缓存       56.0 KiB/token × 32768 × 8 = 14.00 GiB
运行时开销    1.50 GiB
合计          19.84 GiB
缺口          7.84 GiB  ❌ 装不下
  降 bpw 到 Q3_K_M 省 0.79 GiB
  KV 转 q8_0  省 7.00 GiB
  上下文砍半  省 7.00 GiB
```

**注意看这三行建议的差距。** 把权重从 Q4_K_M 再往下砍一档到 Q3_K_M，只省 0.79 GiB，模型还明显变笨；把 KV 缓存从 fp16 降到 q8_0，一刀省 7 GiB，质量几乎无损。

这就是整篇最值钱的一句话：**权重挤不动的时候，别再盯着量化级别了，去看看 KV 缓存。**

## 常见配置对照表

下面是 Qwen3.5 家族配 Q4_K_M 的大致占用。**这些数字来自第三方硬件站点的整理汇总，和实际拉取到的 GGUF 文件大小可能有出入，请以你实际下载的文件为准。**

| 模型 | Q4_K_M 权重 | 建议最低卡 | 32K 上下文后还剩多少 |
| --- | --- | --- | --- |
| 0.8B | 约 0.6 GiB | 核显、纯 CPU 都能跑 | 富余充足 |
| 9B | 约 5.5 GiB | RTX 3060 12GB | 约 4 GiB |
| 27B（稠密） | 约 15 GiB | RTX 3090 / 4090 24GB | 勉强够用 |
| 35B-A3B（MoE） | 约 21.4 GiB | RTX 4090 24GB 偏紧 | 建议上 32GB |
| 122B-A10B | 约 67 GiB | 双 4090，或 Mac 128GB 统一内存 | 看组合方式 |
| 397B-A17B | 约 220 GiB | 多卡服务器 | 不在话题范围内 |

顺带一句关于苹果的。Mac 的统一内存有个很实在的好处，**没有独立显存这个天花板**，M4 Max 128GB 就能把 67 GB 的大家伙整个吃下还剩下 61 GB 给 KV。代价是带宽决定了速度上限，所以它适合「装得下」，未必适合「跑得快」。

## 三个当场能用的结论

**1. 出问题先看 KV，不要急着往更低的量化级别上砍。** 长文档、多轮对话、多人共用，爆的都是这一块。

**2. 估算时务必把并发算进去。** 自己单聊能跑通，不意味着三个人一起用也能跑通。

**3. 留 10% 的呼吸空间。** 把显存卡到 100% 用的人，都被碎片整理和长序列 prefill 教过做人。

## 炼丹小结

1. 显存 = **权重 + KV 缓存 + 运行时开销**，三者缺一不可，只看权重必然踩坑；
2. 权重 = 参数量 × bpw ÷ 8，**GB 和 GiB 差 7.4%**，别被这两个单位绕进去；
3. MoE 模型**按总参数交显存，按激活参数算速度**，别拿激活参数去买卡；
4. KV 缓存 = 2 × 层数 × KV 头数 × 头维度 × 字节数 × 长度 × **并发**，它是唯一随时间线性增长的项；
5. 同参数量的两个模型，KV 占用可以差**两倍以上**，看 `num_key_value_heads` 比看参数量有用；
6. 显存紧张时，**降 KV 精度远比降权重量化划算**；
7. 留给运行时 1.5～2 GiB 打底，**永远别把显存用到满**。
