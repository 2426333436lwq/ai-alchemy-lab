问模型"今天北京天气怎么样"，它会告诉你"我无法获取实时信息"，或者更糟——**编一个**。

因为它只有一张嘴。它不联网、不查库、不能动任何东西。

**工具调用（Function Calling / Tool Use）就是给它接上手。**

## 一个比喻：大脑和手

| | 模型 | 工具 |
| --- | --- | --- |
| 扮演 | **大脑**：理解意图、做决策 | **手和眼睛**：真的去查、去算、去做 |
| 能干 | 判断"现在该查天气" | 真的调用天气接口 |
| 不能干 | 不能真的拿到数据 | 不知道该什么时候被调用 |

**模型负责"决定该干什么"，工具负责"真的把它干了"。**

## 一次完整的工具调用长什么样

以"今天北京天气怎么样"为例，实际发生的是四步：

```text
① 你提问 ────────────→ 「今天北京天气怎么样？」
                              │
② 模型决定 ─────────→  它不回答，而是输出一个"请求"：
                        { "想调用": "get_weather",
                          "参数": { "city": "北京" } }
                              │
③ 你的程序去执行 ────→  真的调天气 API，拿到结果：
                        { "temp": 28, "weather": "晴" }
                              │
④ 结果还给模型 ──────→  模型把结果翻译成人话：
                        「北京今天晴，28 度。」
```

**关键点：模型从头到尾没有真的调用任何东西。** 它只是输出一段结构化的"我想调用这个工具，参数是这些"的文本，**真正执行的是你的代码**。

理解这一点很重要——它意味着**安全边界在你手里**：模型只能在你给的工具列表里选，调什么、参数是什么，你都能校验。

## 工具描述怎么写（这是最容易翻车的地方）

模型靠什么决定"该不该调用这个工具"？靠你写的**工具描述**。

来看个反面教材：

```json
{
  "name": "search_database",
  "description": "Searches the database."
}
```

就一句"搜索数据库"。模型除了知道它是查库的，**什么都不知道**：什么时候该查？传什么参数？失败了怎么办？

结果就是它开始**猜参数**——比如自己编一个 user_id。这就是幻觉在工具调用里的样子。

对比一下合格的描述：

```json
{
  "name": "search_database",
  "description": "根据精确的 email 或 user_id 查询客户记录。\n在建议任何账户变更之前必须先调用本工具，严禁猜测 user_id。\n最多返回 10 条结果，需要更多请缩小查询范围。\n若 email 格式非法会调用失败，请先校验格式。"
}
```

它说清了四件事：**什么时候用、不能干什么、返回什么、失败了怎么办**。

> 💡 这是个通用原则：**工具描述就是写给模型的 Prompt**（第一层第 3 篇的配方原则在这里同样适用）。花十分钟写好描述，能省十小时 debug。

## 从工具调用到 Agent：让循环自动跑

单次工具调用你已经会了。那么 **Agent** 是什么？

> **Agent = 让「模型决定 → 调工具 → 看结果 → 再决定」这个循环自动跑很多轮，直到完成任务。**

一次调用 VS Agent：

| | 单次工具调用 | Agent |
| --- | --- | --- |
| 循环几轮 | 1 轮 | 多轮，直到搞定 |
| 谁决定下一步 | 人 | 模型自己 |
| 例子 | 查一次天气 | "帮我安排下周去上海出差：订机票、订酒店、加到日历" |
| 中途出错 | 人来处理 | 模型看到错误，自己换个办法重试 |

## 一个具体例子：出差助手

用户说：**"帮我查下周五上海天气，如果下雨就提醒我带伞。"**

Agent 的执行过程：

```text
轮次 1  模型想：需要知道"下周五"是哪天 → 调用 get_today_date()
        结果：今天是 2026-09-27（周日）

轮次 2  模型想：下周五是 2026-10-02 → 调用 get_weather("上海","2026-10-02")
        结果：小雨

轮次 3  模型想：答案是"要带伞" → 不再调工具，输出最终回答
        「下周五（10 月 2 日）上海有小雨，记得带伞。」
```

**这就是 Agent 的全部秘密**：一个 `while` 循环，每一轮让模型看着历史决定"继续调工具"还是"给出最终答案"。

```python
def run_agent(user_request, tools, max_turns=10):
    history = [{"role": "user", "content": user_request}]
    for _ in range(max_turns):
        resp = llm(history, tools=tools)
        if resp.wants_tool_call:          # 模型说"我要调工具"
            result = execute(resp.tool_call)   # ← 你的代码真的去执行
            history.append({"role": "tool", "content": result})
        else:                              # 模型说"我可以回答了"
            return resp.content
    return "超出最大轮次，任务未完成"      # 记得设上限！
```

那个 `max_turns` 一定要有——**否则模型可能陷入死循环**，把你的钱烧光。

## 新手必知的四个坑

| 坑 | 症状 | 解法 |
| --- | --- | --- |
| **工具描述含糊** | 模型乱猜参数、调错工具 | 描述写成"契约"：何时用、不能干什么、失败怎么办 |
| **工具太多** | 模型挑花眼，选错工具 | 一次只给它 5～10 个相关工具，别一次塞 50 个 |
| **不设轮次上限** | 死循环烧钱 | 硬性 max_turns，超了就停 |
| **不校验参数** | 模型传了危险参数 | 执行前校验；写库/付款类操作加人工确认 |

## 炼丹小结

1. 模型只负责**决定干什么**，**真的执行的是你的代码**——安全边界在你手里；
2. 工具调用四步：模型输出调用请求 → 你执行 → 结果还给模型 → 模型翻译成人话；
3. **工具描述就是 Prompt**，要写成"契约"而不是"标签"；
4. **Agent = 这个循环自动跑多轮**，本质就是个带上限的 `while` 循环；
5. 一定要设 `max_turns`，危险操作要人工确认。

学会了工具调用，你就从"用模型聊天"跨到了"用模型干活"。

接下来你会发现一个新问题：循环跑久了，历史记录会把上下文撑爆、模型开始犯糊涂——这就是进阶篇《上下文工程》要解决的问题。
