每个能把大模型跑在本地的人，大概都经历过同一种尴尬。

自己笔记本上跑得好好的一个模型，搬到内网服务器给同事共用之后，开始出现三种奇怪的病：**隔十分钟问一句就卡三秒；明明给足了上下文文档，它却说没看到；两个人同时用就有一个直接掉线。**

模型没换，代码没改。差的不是模型，是**「自己一个人用」和「当成一个服务提供出去」之间，隔着七件没人提醒你的事**。

## 一个比喻：家里的咖啡机和办公室的茶水间

给你一个人泡咖啡，问题很单纯：豆子磨好，水烧热，按下按钮。

给一整个办公室泡，就多了四个新麻烦。

- **预热要不要一直开着**。人走光了咖啡机还在烧水，电费在流；关了又让下一个来的人等半天；
- **几个人伸手时要怎么排队**。三个人同时接，出水量还是那么多，谁都接不满；
- **谁来负责加豆加水**。这事没人管，第三天就没人能喝了；
- **隔壁公司能不能进来蹭**。门开着的，人家闻着味就来了。

Ollama 是那台咖啡机。前面两篇我们关心的是「能不能把它点着」，这一篇关心的是这四个新麻烦。

下面七件事按顺序排，越靠前越容易踩，也越容易修。

## 第一件事：先问它「你到底把模型放哪了」

这是所有诊断里性价比最高的一条命令。

```bash
ollama ps
```

```
NAME              ID              SIZE     PROCESSOR    UNTIL
qwen3.5:27b       a1b2c3d4e5f6    17 GB    48%/52% CPU/GPU    4 minutes from now
```

请死盯 **PROCESSOR** 这一列。它的三种读数分别意味着完全不同的事。

| 读数 | 含义 | 该做什么 |
| --- | --- | --- |
| `100% GPU` | 模型整个在你的显存里 | 正常，这是理想状态 |
| `100% CPU` | 一点没进显存，全在系统内存跑 | 会慢一个数量级，查驱动或显存 |
| `48%/52% CPU/GPU` | **被劈成了两半**，一半在内存里 | 最坑的一种，见下 |

第三种是最多人吃了哑巴亏的地方。模型被拆开之后，**住在系统内存里的那部分基本是按 CPU 速度跑的**，它会把整条链路拖到自己那个速度上。结果就是显卡利用率看着很低，输出却慢得像爬。

> **一条能省半天的诊断规则**：看到有人抱怨「显存明明够为什么还这么慢」，先看 PROCESSOR 列。**显存里装不下 ≠ 会报错，很多时候只是悄悄地被切了一半走系统内存。**

同一个模型在两台机器上表现不一致，解释起来并不复杂。回头去看第一篇那张三笔账就明白了：上下文往上翻，显存里挤进来的新东西变多，模型本身就被往外推。

## 第二件事：默认 4096 的上下文，是你所有怪问题的源头

这一条我给它排在第二，是因为它制造的症状最像灵异事件。

Ollama **不是按模型标称的上下文**来分配缓存的，它按你的显卡显存挑一个默认值。按官方 2026 年 8 月的文档，规则是三档。

| 可用显存 | 默认上下文 |
| --- | --- |
| 低于 24 GiB | 4,096 |
| 24 到 48 GiB | 32,768 |
| 48 GiB 及以上 | 262,144 |

于是会出现一个很有喜剧效果的场面：同一个模型，在笔记本上只有 4096 的窗口，搬到工作站上不作任何设置就变成了 32768。**你的模型在两台机器上的表现不一样，而你没改过任何东西。**

症状也就解释得通了。你的文档字数没问题，问题是**窗口只有四千多**，超出去的部分被悄悄截掉了，而且不会报错。

### 这里有个流传很广的错误写法

很多教程和 `.env` 文件里写着这一行。

```bash
OLLAMA_NUM_CTX=24576     # ❌ 这一行是无效的
```

**服务器根本不读这个变量。** 有人直接在官方 Docker 镜像上验证过：设了 `OLLAMA_NUM_CTX=24576` 之后发请求，模型照样按显存默认加载成 32768，一个字都没生效，也不报错。

它之所以传得这么广，是因为 `num_ctx` 这个名字本身是真实存在的——它是请求体里的键名、是 Modelfile 里的参数名、也是交互模式下 `/set parameter num_ctx` 的参数名。人们很自然地推测前面加个前缀就能当环境变量用，**偏偏这一条不成立**。

真正管用的三个写法是这些。

```bash
# 1) 服务端全局默认值
OLLAMA_CONTEXT_LENGTH=64000 ollama serve

# 2) 单次请求里指定
curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.5:27b",
  "messages": [{"role": "user", "content": "..."}],
  "options": {"num_ctx": 64000}
}'

# 3) 写进 Modelfile 固化下来，推荐这种
PARAMETER num_ctx 64000
```

改完之后记得用 `ollama ps` 里的 **CONTEXT 列**确认是否真的生效。**不要相信变量名字，去看实际加载出来的数字。**

### 该给多少

Ollama 自己的建议是：**做网页检索、Agent、编程工具这类活，上下文至少给到 64,000 token。**

对照上面那张三档表你会发现一件尴尬的事——**任何低于 48 GiB 的显卡，默认值都达不到这条线。** 所以只要你打算接 Agent，这一项就必须显式设置，没有例外。

代价也要说清楚。同一份社区测量给出了很直观的数字：一个 1B 模型，4096 上下文占 1.52 GB 内存，16384 占 2.02 GB，65536 直接到 4.00 GB，**平均每多一千 token 多约 40 MB**。模型还是那个 1.3 GB 的模型，内存占用能翻将近三倍。

而这笔账**是乘在并发槽上的**，这一点我们下一节就撞上。

## 第三件事：模型默认五分钟就下班

这是第二个制造「感觉随机」行为的开关。

**最后一次请求之后再过五分钟，Ollama 会把模型从显存里请出去**，腾地方给别人。所以会出现这样的体验。

```text
第 1 句提问      秒回
第 2 句提问      秒回
去泡了杯咖啡回来 卡三秒才出第一个字
```

不是网络抖了，是它下过一次班，现在在重新上班。

这个默认值对开发机是体贴的（省显存），对服务是致命的。改法有三种粒度。

```bash
# 全局：单位可以是 10m、1h，-1 表示永不下线
OLLAMA_KEEP_ALIVE=-1 ollama serve

# 单次请求：用完立刻卸载
"keep_alive": 0

# 单次请求：这一轮之后留十分钟
"keep_alive": "10m"
```

**常驻不等于免费。** 一直驻留意味着这一块显存被它长期独占，别的模型想加载就只能在外面排队等着。

### 并发也不是免费的

这是这一节最容易被忽略的一笔账。

`OLLAMA_NUM_PARALLEL` 控制同时能处理几个请求。听起来像是「白送的性能」，实际不是——**每开一个并行槽，就得多准备一份上下文缓冲**。

```text
1 路 × 32K    一份 KV
4 路 × 32K    四份 KV
```

把它和第一篇那个脚本合起来用：把「64K 上下文 × 4 路并发」代进去，你会发现 KV 那一项**轻松超过模型权重本身**。很多人以为自己还有大半张卡，其实那里一半已经预售出去了。

配套的还有一个 `OLLAMA_MAX_LOADED_MODELS`，决定最多同时驻留几个不同模型。两个都设得很大，是内网服务器 OOM 的头号原因。

> **给一组能直接用的起步值**：单卡 24 GiB 跑一个模型给小团队用，`OLLAMA_NUM_PARALLEL=2`、`OLLAMA_KEEP_ALIVE=10m`、`num_ctx=32768`。先按这组跑一周，看 PROCESSOR 列和显存，再往上调。

## 第四件事：Modelfile 才是那个「配置」

在所有人各自往请求里塞参数的团队里出配置漂移是迟早的事。Ollama 给的正解是 **Modelfile**，把整套参数固化成一个有名字的模型。

```dockerfile
FROM qwen3.5:27b-instruct-q4_K_M

PARAMETER num_ctx        64000
PARAMETER temperature    0.3
PARAMETER num_predict    2048

SYSTEM """
你是「AI 炼丹房」内部的工程助手。回答都用简体中文。
不确定的地方直接说不确定，不要编。
涉及具体版本和价格，一律标注数据来源和核对日期。
"""

PARAMETER stop "<|im_end|>"
```

然后把它造出来，起一个团队统一的名字。

```bash
ollama create alchemy-assistant -f ./Modelfile
ollama run alchemy-assistant
```

好处立刻有三个：**参数不再漂移**、**团队成员用一个名字就能拿到同一套配置**、**系统提示和停止词不用再写进每个请求体**。

从 0.35.1 起 Modelfile 还支持 `CAPABILITY` 声明，可以明确写出这个模型支持哪些能力。如果你接的是 Agent 或者需要工具调用，**务必先确认这个模型的 `ollama show` 输出里列了 `tools`**，没有的话 Agent 会以一种很安静的方式不好使。

## 第五件事：把它真的当成一个服务

前面的配置都还会随着终端关闭而失效。到了这一步，我们才把它变成一个「开机就有」的东西。

先说一个必须先讲的硬事实：**Ollama 的原生接口没有内置鉴权。** 谁能连到那个端口，谁就能用你的显卡、读你加载的模型。它在容器网络和内网里尤其危险。

> **把它绑在 `127.0.0.1` 上，前面用反向代理挡一层**，是成本最低的正确做法。直接把 11434 暴露到办公网，等于在公共楼梯间放了一台不要钱的咖啡机。

一份可以直接落到 `/etc/systemd/system/ollama.service` 的参考。

```ini
[Unit]
Description=Ollama Service
After=network-online.target

[Service]
Type=simple
User=ollama
Environment=OLLAMA_HOST=127.0.0.1:11434
Environment=OLLAMA_KEEP_ALIVE=10m
Environment=OLLAMA_NUM_PARALLEL=2
Environment=OLLAMA_MAX_LOADED_MODELS=1
Environment=OLLAMA_CONTEXT_LENGTH=64000
Environment=OLLAMA_FLASH_ATTENTION=1
Environment=OLLAMA_KV_CACHE_TYPE=q8_0
ExecStart=/usr/local/bin/ollama serve
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

几个值得说明的点。

- **`OLLAMA_HOST=127.0.0.1`** 而不是 `0.0.0.0`。对外就交给 Nginx 反代，顺手把 Basic Auth 或者公司 SSO 那一层加上；
- **`OLLAMA_KV_CACHE_TYPE=q8_0`** 正是第一篇算出来的那个结论，KV 换 8 bit，几乎无损地省一大块；
- **`OLLAMA_FLASH_ATTENTION=1`** 开启 Flash Attention，长上下文收益明显，前提是你的驱动和卡支持；
- **用独立的 `User=ollama` 跑**，别图省事用 root。

改完之后。

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ollama
systemctl status ollama
```

对外的话，它还顺便提供了一个 **OpenAI 兼容接口** `http://localhost:11434/v1`，绝大多数现成客户端改个 base URL 就能连，API key 那栏随便填个 `ollama` 即可。

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")
r = client.chat.completions.create(
    model="alchemy-assistant",
    messages=[{"role": "user", "content": "把这段日志按错误类型归类"}],
)
print(r.choices[0].message.content)
```

## 第六件事：升级之前必须先看变更清单

这一条听着像废话，但它是这一篇里唯一能让你免于「昨天还好好的」的方法。

Ollama 版本迭代很快，最新稳定版是 **v0.40.0（2026 年 9 月 25 日发布）**。这一版在 Apple Silicon 上做了一个改动：**对支持的模型架构，默认改走 MLX 运行时**，不需要任何配置。支持的名单里除了这一版新增的几个系列，还包括几类「决策模型」和一个 embedding 模型。

> **请把它看成一个行为变更，而不只是一个性能提升。** 默认运行时换了，意味着内存占用曲线、吞吐、乃至分词行为都可能跟着动。有人在上线前的建议写得很实在：升级前先钉住旧版本，把基线提示词、输出、延迟、资源占用都抓一份，升级后逐项比对。

当时还有第三方整理的每日汇总列出了一批尚未修复的回归项（涉及多模态输入被静默丢弃、接口参数未按预期生效、拉取时磁盘满导致静默失败等）。**这类清单的状态每天都在变，不要照着它做决策**，但它说明了一件事：**新版本带着回归是常态，把这个假设写进升级流程里，比记住任何一个具体 bug 有用。**

## 第七件事：知道它什么时候不够用

最后要给 Ollama 的边界画条线，不然你会拿它去做它不擅长的事。

Ollama 的底子很清楚：**MIT 协议，底层跑的是 llama.cpp 引擎**，主打单机、开发者友好、脚本和 Agent 集成。这一层让它非常适合「一台开发机 + 一个小团队 + 一堆脚本」这种场景。

但有几件事，它本来就不是为这种场景设计的。

| 你的情况 | 该往后看什么 |
| --- | --- |
| 大量请求共享同一段系统提示（RAG、多轮） | 需要显式的前缀复用，去看服务端引擎 |
| 多人并发、要稳定的 P95 延迟 | 需要连续批处理和显式的调度策略 |
| 要 Prometheus 指标、要细粒度并行 | Ollama 这一层不提供 |
| 只在 Mac 上追求单机极限 | 可以直接试 MLX 系 |
| 想要图形界面、点几下就能挑模型 | LM Studio 这类商业软件自 2025 年 7 月起允许在工作场景免费使用，留意它仍是闭源协议 |

一句话总结它的边界：**Ollama 是本地部署里最好的「第一台」，不是「最后一台」。**

下一篇《引擎选型与并发压测》，我们会把桌子上剩下的几个选手摆出来——llama.cpp、LM Studio、vLLM、SGLang、LMDeploy——讲清楚它们各自适合哪种活，以及为什么同一个模型换个引擎吞吐能差一个数量级。

## 炼丹小结

1. 诊断一律从 `ollama ps` 的 **PROCESSOR 列**开始，`100% CPU` 或混着跑，就是慢的根源；
2. **默认上下文按显存分三档**，同一模型在不同机器上可以差八倍，且截断时不报错；
3. **`OLLAMA_NUM_CTX` 是无效变量**，用 `OLLAMA_CONTEXT_LENGTH`、`num_ctx` 请求参数或 Modelfile，改完用 CONTEXT 列验证；
4. 接 Agent 至少 **64,000 token**，任何低于 48 GiB 的卡默认都不达标；
5. 上下文内存**乘在并发槽上**，这一项常常超过权重本身；
6. **模型默认五分钟卸载**，`keep_alive` 支持 `-1`、`0`、`10m` 三种写法，生产按需调；
7. 团队用请把配置写进 **Modelfile**，避免每人各自传参导致漂移；
8. **原生接口没有鉴权**，绑 `127.0.0.1` 加一层反向代理，别直接暴露到办公网；
9. **升级先看变更清单**，把「默认运行时可能变了」当成默认假设；
10. 它是本地部署最好的第一台机器，**多人高并发就换引擎**。

Ollama 把「跑起来」这件事做到了一键，这是它最大的功劳。剩下的「跑得好、跑得稳、不被人蹭」，还得你自己动手。
